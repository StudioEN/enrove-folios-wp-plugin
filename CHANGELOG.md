# Changelog

## [Unreleased]

### Changed
- A folio's pages now go live with their folio, never ahead of it. While a folio is unpublished, none of its pages can be published, scheduled or made private: the page editor says so in a notice at the top, with a link to the folio, and offers only Draft and Pending, with Submit for Review as its main button, the way it does for a Contributor (a publish sent some other way fails with the reason rather than quietly saving a draft); Quick Edit on the Pages tab no longer offers Published, Scheduled or Private. A live page moved into an unpublished folio goes back to draft too. Unpublishing a folio, from its editor, Quick Edit, Bulk Edit or the trash, or deleting it outright, returns its live pages to draft. Publishing it again, from its editor, from Quick Edit or on its scheduled date, puts those pages back as they were (a private page stays private, a scheduled one keeps its date) and publishes its other draft and pending pages; a folio made private brings back only the pages that were private, and the rest wait for it to be published. Once a folio is live, each page can be unpublished or published on its own, and saving the folio (or its autosave) no longer publishes pages that were taken down. Private folios count as published. A page taken down in a published folio also leaves the folio for everyone, its editors included: signed-in editors used to see the folio's draft and pending pages in its navigation, previous and next links and table of contents, so a page they had unpublished still looked part of it. An unpublished folio still previews with all its pages for its editors. Updating from an earlier version, a site whose unpublished folios still have live pages (Unpublish used to leave them as they were) has those pages returned to draft once, on the first wp-admin request after the update; they come back when their folio is published. A WordPress import keeps each page's status as exported, and a duplicated folio's pages start as plain drafts.
- Publish and Unpublish in the folio editor now ask first, in a dialog that says how many pages go live or back to draft with the folio. A Contributor's Submit for Review changes no page and does not ask.

### Fixed
- Text that could not be translated now can: the editor labels, placeholders, titles and descriptions of the eBook and Proposal blocks; the folio editor's Setup tab; the admin's save messages, footer and Quick Edit strings; and what readers see in the eBook, Magazine and Proposal themes (Contents, Back to top, Previous and Next, the navigation and light/dark toggle labels, the callout box's Note/Tip/Important/Warning, "(optional)" in the pricing table). Block sample content stays as written. The Subtitle and Copyright placeholders read "Optional" instead of "Option".
- Opening a page of a private folio without the right to read it reported "Theme not found", as if the folio's theme were missing. It now says the folio is not published, like any folio the visitor cannot see; a page is checked against its folio's visibility first.
- Changing a folio page's status on someone's behalf (publishing a folio, which publishes its pages) re-saved the page's content through the save filters of whoever was doing it: WordPress's HTML filter, and from WordPress 7.0 its block custom CSS filter. For an Author, an administrator on multisite, or a scheduled folio going live by cron, that could strip embeds, SVG, forms and block CSS an administrator had put in a page. Status changes now leave the title, content and excerpt exactly as stored.
- Two request values are sanitised where they are read (the folio base slug on Settings → Routing, decoded first so a non-ASCII slug keeps its characters, and the request path the front end matches folio URLs against), and the admin's inline settings are encoded so no value in them can close or comment out their script.
- The folio page editor's content ran edge to edge, with no side padding and no reading column, on a site whose WordPress theme is a block theme (Twenty Twenty-Five, the default on a new site, among them). Core's global styles reset the canvas padding and widen the post content to the full width, and with the site theme's `theme.json` kept out of the editor nothing set the content width back. The canvas now sets the column width a block theme's layout reads, and its side padding holds against core's reset. On a classic site theme the canvas text had also fallen back to the browser's serif at its default size and line height, because core's editor reset outranked the canvas's own type; it now ties with the reset and wins.

## [0.5.1] - 2026-09-29

### Added
- A setup dialog the first time an administrator opens a Groove screen. A site installed from WordPress.org has neither the theme fonts nor the sample photos, since neither can ship in the plugin, and until now nothing said so: folios quietly fell back to system fonts and blank covers, which made the themes look plainer than they are, and the only way to fix it was two buttons on two Settings tabs. The dialog says what each download is, where it comes from and roughly how big it is, and offers a real alternative for each: **Download from Google Fonts** or **Use system fonts**, and **Download from Pexels** or **Use gradient covers**. The button always says what it will do ("Download fonts and photos", "Download photos", "Save choices"). Pressing it runs the downloads in short steps with a progress bar for each, so a slow host shows progress instead of timing out, and closing the dialog mid-download does not stop it; a failure names the item and the reason and offers Try again. The dialog opens by itself only once per administrator. Closed without choosing, it leaves a **Finish setting up** panel at the top of Overview, in place of the welcome line, and a **Finish setup** button in the header of the other Groove screens (not the folio editor), and both stay until each item is settled. Nothing is fetched until the button is pressed, and editors and other non-administrators are never asked.
- A **Reset** tab on Groove → Settings, for troubleshooting and for going through the first-run setup again. **Reset Groove Folios…** opens a confirmation that lists what a reset does: every setting on the Settings tabs goes back to its default (the Pexels API key stored there included), the downloaded fonts and photos are deleted and the choices about them forgotten, and the setup dialog is shown to every administrator again. When the site has folios, the dialog says how many folios, pages and collection tags there are and asks whether to **Keep them**, the default, or **Delete them too**, permanently and trash included; only then does a red "can't be undone" warning appear and the button change to "Reset and delete folios". The reset lands on Overview, where a fresh install starts, with a toast saying what happened. It leaves alone the markers of one-time data migrations, every Media Library item (sample images copied there included), and a Pexels key set in `wp-config.php`, the environment or a `.pexels-key` file.
- **Remove Downloaded Fonts** on Settings → Fonts and **Remove Downloaded Photos** on Settings → Imagery. Each deletes that download from `uploads/groove-folios/` and forgets the choice made about it, so the site is back where a fresh install starts for that item: the Finish setup panel and header button return, and the setup dialog offers the choice again. Removing photos leaves photos carried in the plugin alone, and featured images that sample content already copied into the Media Library stay; pictures inside sample folios go missing until the photos are downloaded again, which the button's note says. There is no confirmation step, as a download puts everything back.
- Covers without a photo show a soft gradient in the theme's own colours instead of an empty pane, on Folio Starter, Groove eBook, Groove Magazine and Groove Newsletter; Groove Proposal already leaves its photo strip out. The same wash stands in for the feature image preview in the folio editor, which showed a broken image. A theme uses it through `Base_Theme::get_cover_fallback_class()` and `get_cover_background_style()`, and can set `--folio-cover-fallback` for a gradient of its own (`themes/README.md` §6).
- Every Groove dialog (theme details, Add New, Change theme and the setup dialog) now stops 48px short of the top and bottom of the window, so a tall one never runs to the edge. The Pexels API key card on Settings → Imagery now names the curation command in its description, and the separate Curating Imagery card, which only held that command, is gone.
- A download button on the Spec and Playbook tabs of Groove → Themes. It sits at the end of the "Rendered from…" line, beside the name of the file it downloads, and saves that Markdown file (`README.md` or `BUILDING-A-THEME.md`) under its own name, the name the two documents use when they point at each other. It is an icon button like Copy link in the folio editor, with a one-word "Download" tooltip and the full name for screen readers, "Download README.md". A tab whose file is missing from disk shows no button, as there is nothing to download.

### Changed
- Links inside Groove's admin screens now carry a short-lived signature, and a screen reads which folio, tab, filter, search, sort or page to show only from a signed link. Every link and form the plugin draws is signed, so nothing changes in use. A link that is not, such as a bookmark, one older than a day, or one saved before logging out, opens the screen's default view instead: the list unfiltered, the Setup tab, or, for a folio, All Folios with a note that the link has expired. This answers WordPress.org's review, which asks that every request parameter be checked against a nonce before it is read. The front end is unchanged: published and preview folio URLs are public, and their `?folio_id=`, `?p=` and `?groove_preview=` are now registered as query vars and read the way WordPress reads its own.
- A folio page's body is now escaped where it is printed, against the markup WordPress's post editor allows plus what rendering adds: embed iframes (YouTube, Vimeo, Spotify, SoundCloud, WordPress posts), the icons of social links and the image lightbox, the Search block's form, `<source>`, and a featured image's `srcset`. Two things readers may notice. Embeds that need their provider's script to draw (X, Instagram, TikTok) now show the provider's own fallback, the quoted post with a link to it, rather than the live card. And a `<script>` or `<style>` inside a Custom HTML block no longer reaches the published folio. A theme can widen the allowed markup with the `groove_folios_content_allowed_html` filter.
- The CSS that sets a folio's fonts, and the password gate's colours and fonts, are checked again where they are written into the page: each font family must be a plain or quoted name, so one with a stray quote is dropped on its own rather than breaking the rest of the rule, and each colour must be a hex colour.
- A new folio page joins its folio when Add Page opens the editor, from a link whose signature is checked before the folio is read, and only when you may edit that folio. An Add Page link opened after it has expired shows WordPress's "The link you followed has expired" screen, whose link back leads to the folio for a fresh one. No save hook reads a folio from the request or the Referer header any more, and the block editor, the breadcrumb back to the folio and the theme's block list all read the page's own stored folio.
- Folios load their fonts from your own site, never from Google. Every theme is typeset in open-licence Google Fonts families, and each reader's browser used to fetch them from `fonts.googleapis.com` and `fonts.gstatic.com`, handing Google the reader's IP address with no opt-in. WordPress.org's review counts that as phoning home. A new Fonts tab on Groove → Settings has a **Download Fonts** button that fetches every family the plugin can use (about 110 woff2 files, 4 MB, every script subset Google offers) into `uploads/groove-folios/fonts/`, one stylesheet per family rewritten to point at the local files. Folios, the theme previews, the password gate and the folio page editor all load those. Until the fonts are downloaded, and for any family that failed, a folio uses the system font stack the WordPress dashboard uses (Georgia for a serif role). Settings → Fonts also has **Use System Fonts**, for a site that would rather not fetch anything from Google; it keeps any downloaded files, so **Use Theme Fonts** switches back at once. The folio editor says under the font pickers when readers will see system fonts instead of the ones chosen. A press that runs long on a slow host stops starting new families after 20 seconds and says how many are left, so a second press finishes the job rather than the request timing out half way. Download Photos on Settings → Imagery now does the same. The `google_family` key in a theme's `setup.php` is unchanged: it now names what the download fetches.
- No "Powered by Groove Folios" or "Theme designed by …" credit appears on a folio any more. Four of the five themes printed one on the cover or in the page footer, and WordPress.org allows a public credit only when the site's administrator has opted in. The markup is gone, with a comment left where each credit stood. Where a credit was the middle cell of a three-column footer, the empty cell stays so the previous and next links keep their places, and is hidden on phones, where it had a row of its own.
- The inline `<script>` and `<style>` blocks are gone from the plugin's output; everything goes through `wp_enqueue_*()` and `wp_add_inline_*()`. The Themes screen's dialog and contents-rail scripts moved to `assets/js/groove-themes.js`, loaded only on that screen. Groove Magazine's and Groove Proposal's light/dark bootstrap now prints in `<head>` rather than at the top of `<body>`, which is earlier, so the flash it prevents has even less chance.
- A folio page's block inserter offers only the blocks its folio's theme can style. Every theme's blocks used to be offered on every page, so a Groove Magazine page listed Groove Proposal's pricing table and Groove eBook's epigraph, which render there without any styling because their CSS lives only in their own theme. Other themes' blocks are now out of the inserter, the slash menu and the block search. They are hidden, not removed: a page that already holds one, after a theme switch, still opens and edits it, and switching back brings it all back. Such a block now carries a quiet one-line note above it in the editor, such as "Groove Proposal block: Groove Magazine doesn't style it, so readers see it unstyled." This matters because the block still looks finished in the editor, where its own editor styles load, while readers get it plain. The note is editor-only and never saved into the page. A block belongs to a theme when its name starts with the theme's ID (`groove-proposal/…`), the same rule the Change theme dialog uses to count what a switch would affect. A folio with no theme set follows the default theme, as it does for readers. Core and third-party blocks are offered on every theme as before.
- The folio editor's save status (Saving…, Saved, Draft saved, Save failed) now appears with every other Groove notification, in the toast stack at the bottom right, instead of in a pill of its own at the bottom centre. It is still one pill that changes as the save runs, not a new one for each step, and it can be dismissed and held open under the pointer like any other toast. While saving it is blue rather than yellow, since a save under way is not a warning.

### Removed
- Installing a folio theme from a .zip on Groove → Themes, together with replacing and removing installed themes. The installer copied the package's PHP into `wp-content/groove-themes/`, and WordPress.org does not allow a plugin to write executable code outside its own folder. The screen now says that support for third-party themes is coming soon. The built-in themes, the Spec and Playbook tabs, and the panel naming theme folders that failed to load are unchanged. A site that installed a package in an earlier version keeps the files in `wp-content/groove-themes/`, but they no longer load, and a folio using one shows the "Theme not found" page until it is given a built-in theme.

### Fixed
- Move to Trash, Restore and Delete Permanently on a folio's Pages tab did the work, but ran after the screen had started drawing, too late for the redirect back to the list, so the screen could stop part-way instead of showing the updated list and its toast. The action now runs before anything is drawn, as it already did on All Folios.
- Duplicate in the All Folios bulk menu checked whether you could delete each folio rather than edit it, unlike the row's own Duplicate link. Both now ask for the right to edit the folio being copied.
- Viewing a folio page no longer writes to the database at all. A page missing its link to a folio used to have it filled in from the URL when an editor viewed it; nothing needs that now that a page is linked when it is created.
- The block editor no longer shows the title of whatever folio a hand-edited `?folio_id=` names; it shows the page's own folio, and only to someone who may edit that folio.
- Groove Magazine ignored a folio's font choices. It declared its font tokens on `:root`, but the folio's fonts arrive as variables on the cover and page roots, and a custom property is worked out where it is declared, so the theme's own STIX Two Text and Inter always won: picking Poppins for a magazine folio changed nothing, and without downloaded fonts the headings asked for STIX Two Text, which shows only on computers that happen to have it installed (Macs do). The font tokens are now declared again on the theme root, the way Groove Proposal already did, so a folio's choice applies and the system-font fallback reaches magazine folios like every other theme.
- Renaming a folio page in the classic editor or Quick Edit ran the slug update a second time and left a broken callback behind. The callback that renames the slug unhooked itself around its own save with `remove_action(…, __FUNCTION__)`, but inside a closure `__FUNCTION__` is `{closure}`, which names no registered callback: nothing was removed, so the save came straight back into it, and the matching `add_action()` registered `{closure}` as a callback that does not exist, a fatal error on PHP 8 if that hook fired again in the same request. It now holds itself in a variable and unhooks that.
- The status links above the All Folios list (Published, Drafts and so on) were built with `translate_nooped_plural()` on the status's registered plural strings, which the translation parser cannot read. They now show the status's own translated label with the count.
- A Contributor could publish a folio. The folio editor is open to anyone who can edit posts, and its Publish checked only that the user could edit that folio, not that they could publish, so a Contributor's Publish put the folio and every page in it live, which WordPress itself never lets a Contributor do. Their button now reads **Submit for Review** and saves the folio as Pending, leaving its pages as they are, the way core's editor does. A new folio also starts as a draft for them when the default folio status is Published. Authors, Editors and Administrators are unaffected.
- A Contributor's page could go live without review through someone else's folio. A page joins a folio through its `folio_id`, which could be set to any folio, from the block editor or with `?folio_id=` on a new page, and publishing a folio published every page linked to it. A page now joins only a folio the person saving it may edit, on every route (the block editor answers a refused link with a 403 before creating anything), and `folio_id` is now protected meta, so it no longer appears in the Custom Fields box. Publishing a folio publishes only the pages the publisher could have published themselves; any other page linked to it keeps its status.
- A Contributor could open anyone's folio in the folio editor, drafts and private folios included, by changing `folio_id` in the address. Saving was already refused, but the fields were on screen. The editor now opens only folios the user may edit, and sends anyone else to All Folios, as core does with posts.
- Viewing a folio page could write to the database. A page missing its link to a folio used to have it filled in from the URL on every view, by anyone, logged in or not. The repair now happens only when the viewer may edit the page.
- The Pexels API key handlers (save, remove, test connection) are registered only in a development checkout, alongside the curation script they serve. The released plugin already hid their settings, but a hand-made request could still reach the connection test, which contacts `api.pexels.com`.
- The folio editor's header buttons (Add Page, Preview or View, Save, Publish or Unpublish) and the Publish button's progress labels were untranslatable English; they now go through the `groove-folios` text domain.
- The last inline JavaScript left in the admin markup is gone: the confirmations before deleting a collection tag or removing the stored Pexels API key, and the revision log's Show all / Show less, are handled in `assets/js/groove-main.js`. Show all now becomes Show less when the older rows appear; the label used to stay put on the first press and then run a step behind the rows, because the text it compared against was padded with whitespace.
- `bin/check-theme-contract.php` stopped checking the cover root of any theme that adds the gradient-cover class through `get_cover_fallback_class()`: the echo made the class attribute look like runtime PHP, which the checker skips. It now reads that helper's call as the known text it is, so Groove eBook's and Groove Newsletter's cover roots are checked again, and its self-test passes.
- The Pexels credits file is no longer written by code that ships. `Credits` could write `credits.json` into the plugin folder; only the build-time curator ever did, so the writer moved into `pexels/curator.php`, which, like `bin/curate-pexels.php`, is left out of the release zip.
- The site's WordPress theme no longer reaches a folio. A folio renders in its own folio theme, but the site theme still got in two ways. In the block editor, a folio page took the site theme's background, fonts, heading weights and colour palette, so a Groove Magazine page on a site running a warm-grey block theme was edited on warm grey in that theme's heavy sans, looking nothing like what readers see. On the published folio, the same global styles and the site theme's own stylesheets loaded under the folio theme, which covered most of them but not all: heading weights, link and button styles, text smoothing and a dark-scheme palette still leaked through wherever the folio theme was silent. Both places now leave out, for that one request only, the site theme's `theme.json` (and its parent theme's), its Site Editor styles, its editor presets, the Customizer's Additional CSS, and every stylesheet the theme loads from its own folder. On the published folio its scripts are left out too. Nothing is changed or saved on the site; every other page and every other editor screen keeps the site theme as before. The folio page editor now shows a plain white canvas with dark text and a centred column, in the folio's own fonts wherever its theme loads them into the editor (Groove eBook and Groove Proposal do). It offers WordPress's default colour palette and sizes instead of the site theme's, so a colour picked from the site theme's palette on an existing page no longer shows, just as it would after a theme switch.

## [0.5.0] - 2026-09-27

### Added
- `SECURITY.md`, which says how to report a vulnerability privately, through GitHub's Report a vulnerability form rather than a public issue, and that only the latest release receives fixes.

### Changed
- Change theme in the folio editor opens the same dialog as choosing a theme for a new folio: the same frame, the same cards with the Selected badge on the corner, a Preview link under each, and arrow keys that move the selection. It used to be a wider dialog of its own, with larger cards, each theme's description, a bordered close button and a Done footer, so the one decision looked like two. The descriptions are gone from the cards because the selected theme's description is already on the Setup tab beside the Change theme button. Both dialogs now render the card from one method, `Add_New::display_theme_card()`, and move the selection with the same script, so they cannot drift apart again.
- Changing a folio's theme asks first when the switch would take something off the folio. A switch deletes nothing — page content is untouched and every theme setting survives the save — but it can change what readers see. Blocks from Groove eBook or Groove Proposal still render under another theme, just without their styling, which lives only in their own theme's stylesheet; and a proposal's client, contacts, date and cover button text show only in Groove Proposal. So when the theme being left has any of that on this folio, Switch theme turns the dialog to a second screen titled with the question — "Switch to Groove Magazine?" — showing the two themes side by side, then which pages and which details, with Back to choose again and Switch theme to confirm, and says that switching back brings it all back. The screen takes the grid's place and its height, so the dialog does not grow to ask. A folio with nothing to lose switches without the question. For that to be possible, picking a card now only chooses it and Switch theme applies it: the theme used to be applied, and autosaved, on the click — or on each arrow-key step through the cards — so there was nothing to confirm before it had already happened, and Cancel could not take it back.
- Remove theme on Groove → Themes asks on a second screen of the theme's dialog, the way Change theme does. It used to open a red box under the action row, which made the dialog taller and put the question below the buttons it was asking about. Now the details step aside and the question takes their place and height. The title becomes "Remove Groove Docs?", and a red notice says the removal can't be undone, that the files are deleted from the site and need the .zip to come back, and how many folios would show readers a "Theme not found" page, with a link to them. Back slides the details back, with focus on Remove theme. Remove theme is now a filled red button, so it can't be mistaken for Create a folio. The screens, the slide and the notice are shared `g-dialog-screen` / `g-dialog-confirm` styles, yellow when nothing is lost for good and red when something is deleted, so the next dialog that has to ask uses the same pattern.
- The folio editor's header has the same actions on every tab. The Pages tab used to show only Preview, so Save, Publish and Copy link disappeared the moment you switched to it, and the Preview button slid across into their place. Now Preview, Save, Publish (or Unpublish) and Copy link sit in the same spots on Setup, Pages and Proposal, and you can publish a folio or copy its link straight from its page list. Save is greyed out whenever there is nothing to save, the way the Settings forms already work: it lights up when a field on Setup or Proposal differs from what is stored, and goes quiet again once an autosave, a manual save or a publish has stored it, or when the edit is undone. It is also switched off while a save is in flight, so a double press cannot save twice. Pressing it while greyed out explains why; on the Pages tab it says that pages save in the page editor.

### Fixed
- Copy link on a draft folio copied a public address that doesn't work yet. It now copies the preview link until the folio is published, then the public link.
- Publishing a folio no longer clears its collection tags when the tags field was not part of the save.
- With reduced motion turned on, closing the Add New dialog left it covering the page invisibly and swallowing clicks, because it waited for a fade that never ran.
- The Vite dev server was never detected, so a development checkout always fell back to the built CSS. The probe asked with HEAD, and Vite answers HEAD on `/@vite/client` with a 404; it asks with GET now. Sites that are not `local` or `development` still never probe.
- The Vite toolchain is updated to clear Dependabot alerts (vite, postcss, nanoid, picomatch). These are development dependencies only, and the built CSS is byte-identical.

## [0.4.0] - 2026-09-23

### Added
- A Download Photos button on Settings → Imagery, and with it a plugin that no longer needs to carry its photographs. Every theme cover and sample-content photo is a Pexels photo, and the Pexels licence forbids redistributing unaltered copies, which the GPL requires anything in the WordPress.org plugin directory to allow. So the WordPress.org package leaves the 46 JPEGs out, and a site fetches its own copy from `images.pexels.com` when an administrator asks for it. The section says how many of the photos the site has, and nothing is fetched until the button is pressed. The download needs no API key: the curator now records each photo's `src_url` in `credits.json` (backfilled for the existing 46), and `Groove\Pexels\Library` fetches the same bytes from the same address into `uploads/groove-folios/photos/`, checking that each one really is a JPEG before it is kept. Photos resolve bundled-first, so a development checkout behaves exactly as before. Sample content seeded before the download points at where the photos will land and fills in once they arrive. Covers do the opposite: a missing cover is an empty string rather than a URL to nothing, so each theme falls back to its own background, and Groove Magazine no longer builds a slide around it. Add New's sample-content tooltip says the photos are missing while they are, because page featured images are attached only at seed time.
- `readme.txt`, which is what WordPress.org reads. It includes the External services section the directory requires, covering Google Fonts (the reader's browser, on published folios) and the Pexels photo download (your server, on request), and it credits the bundled eicons font and the compiled Tailwind with their licences.
- The two theme documents are readable in the admin, as Spec and Playbook tabs on Groove → Themes. They have always shipped with the plugin, and three places on that screen told you so by printing `themes/README.md` in a sentence — which is a path, not a door: it assumes the reader has a checkout, a file manager and a Markdown viewer, none of which a site administrator looking at a theme that will not load necessarily has. The files are rendered where the question is asked. Nothing is copied: `Groove\Utils\Markdown` reads the same file on disk, so there is no second version of this text in `pages/` for an edit to miss — the same reason a theme's description is read from its own `setup.php` — and each tab says which file it came from, because the next thing someone who disagrees with the spec wants is where to change it. Headings carry the anchors GitHub would give them, so `#13-known-warts` resolves in both places and a section can be linked to a colleague; the cross-references the two documents already make to each other become links between the two tabs; and a relative path to a file in the repository renders as the path it names rather than as a link that 404s, because there is nothing in wp-admin to open.
- The panel naming theme folders that did not load links to the playbook's section 9, which is a table of every fault a loader can record. The panel already said what went wrong and what to do about it in a sentence; what it could not do was explain the class of problem, and the only document that does was a file path. Linked once under the heading rather than on each of the nine possible rows, since they would all point at the same table. The anchor is a constant in `Groove\Utils\Theme_Docs` rather than a string in the page, so `bin/check-docs.php` can prove it still names a heading that exists — a section renamed out from under it would otherwise turn the link into a silent jump to the top of the page, which is exactly the kind of breakage these documents spend eleven hundred lines warning about.
- A contents rail on both document tabs, listing each document's top-level sections and marking the one being read as you scroll. Eleven hundred lines is past the point where a reader can hold the shape of a document in their head, and the spec's thirteen numbered sections were only findable by scrolling until one appeared. Top-level only: the first cut nested the `###` subsections under them and took the playbook's rail from eleven entries to thirty-five, which is a second copy of the document rather than a way to find your place in it — a contents list you have to scan is not doing the one job it exists to do. The subsections are still headings on the page, still anchored, still linkable. It is a side rail once the card is wide enough for one and a stacked box below that, measured with a container query rather than a media query, because the admin menu is 160px wide — or 36px folded — so the viewport is wrong about this screen's width by the whole menu. Clicking an entry glides to the section rather than cutting to it, so the reader can see where they have been put — as does a cross-reference in the prose, which is the same gesture and should not behave differently; a reader who has asked their system for reduced motion gets the cut. The marking and the glide are the only parts that need JavaScript, and both degrade to a list of links to anchors that exist, which is the half that makes a document navigable.
- `bin/check-docs.php`, which is what makes a hand-written Markdown renderer safe to rely on. `Groove\Utils\Markdown` implements the Markdown these two files use rather than Markdown in general — a deliberate trade, given there is no Composer here and the alternative was vendoring a parser unmaintained since 2019 to gain edge cases these documents do not contain. The cost of that trade is that unsupported syntax raises nothing: it renders as literal asterisks and pipes in the middle of the spec, which reads as a broken page with nothing to say why. So thirteen rules reject what the renderer cannot do — images, footnotes, reference links, strikethrough, raw HTML, autolinks, entities, underscore emphasis (these files are full of `snake_case`), setext headings, lazy blockquote continuations — and three more check the output rather than the input: no Markdown survived into the HTML, no table row disagrees with its header about how many columns it has, and every anchor linked to still exists. Each rule was checked by breaking a copy of a real document and watching it fire, because a rule that never fires looks exactly like a document with nothing wrong in it. It shims the five escaping functions it needs, so like the contract checker it runs on a bare checkout with no WordPress.

### Added
- `bin/check-theme-contract.php` reads the theme's JavaScript. It never had, which left the whole runtime-repaint half of the token contract — forty-odd lines of README §7 — with nothing verifying it, and that is how the Newsletter bug above survived. The rule is narrow on purpose: theme JS that writes a custom property must write the `--folio-*` slot, not a private the theme's own CSS declares as `var(--folio-*)`, because an inline value on the alias renders correctly and leaves the slot stale. Only aliases are flagged. A private holding a literal has to be written directly — nothing points at it, and all three repainting themes write plenty of those deliberately — so flagging every private write would have been noise rather than a rule. Three selftest cases, and two of them are the quiet kind: setting the slot, and writing a private that holds a literal, both have to stay silent, because a check that cries wolf gets switched off as surely as one that says nothing.
- The Themes screen names the theme folders that did not load, and why. Seven guards across the two loaders skipped a malformed theme with a bare `continue` — no log line, no notice, nothing — so a theme that failed one simply was not in the picker, and the only way to find out why was to read the loader. It used to be refused outright — "remove the installed theme first" — which made shipping a revision a two-step chore and meant uninstalling a theme that live folios were using. ### Changed
- The docs record what happens when a theme file is broken, and correct the folklore they used to repeat. Theme files are `require`d from `Plugin::__construct()` at file scope, before any hook fires, with nothing in the call stack that catches anything — so a broken theme file is not a skipped theme, it is a white screen on the front end, in wp-admin, in REST and in cron, and wp-admin is the part that hurts, because Groove → Themes is where the operator would have gone to remove it. That much was already written down. What was written down next was wrong: that a syntax error in an included file is an uncatchable fatal and therefore structural. It has been a catchable `ParseError` since PHP 7.0, which is this plugin's floor — verified, along with a class extending a missing parent and an undefined function called at file scope, both plain `Error`. All three bring the site down only because the loaders do not `try` around the `require`, which is a small local change against machinery that already exists, not a boot restructure. The genuinely uncatchable one is narrower than claimed and was never the one being described: `Cannot redeclare class X` is an engine fatal rather than a `Throwable`, which is why `install_theme_from_zip()` refuses ID and class collisions outright instead of warning about them. `themes/README.md` §13 carries the table and the trap waiting for whoever wraps those requires — a parentless class is declared at compile time, so a file that aborts mid-execution can still leave `class_exists()` true, and a catch that falls through to the class guards would register a half-initialised theme. The root `README.md` gains the operational half: lint with `php -l` before deploying, because the contract checker tokenises and cannot catch a syntax error, and install packages through the Themes screen rather than unzipping into `wp-content/groove-themes/` by hand.
- A theme declares its password-gate colours in `setup.php`, and the two hardcoded ID maps in `includes/folio-preview-template.php` are gone. They were plugin source with no filter to join, so a theme shipped as a package could never appear in them — which made the contract rule for it the one check no third-party theme could ever pass, satisfiable only by patching plugin core, which the next update overwrote. A `gate` block carrying `accent`, `accent_hover` and `background` sits beside the `fonts` block, in the file the theme owns. All three are run through `sanitize_hex_color()` and anything that is not hex is dropped, because they are interpolated straight into the gate's inline CSS and an installed package is not trusted input; a theme that declares nothing falls back to the plugin's neutral, which is what the maps did for an unknown ID anyway. The checker's rule moved with it, and its two selftest cases became three — the third being a value that is not a colour at all, which is the one that matters most.
- Contract findings moved onto the theme they describe, and joined the skipped folders in one panel. They were handed to the next page load in a per-user transient that the first render drained — so a reload lost them, and a second admin never saw them at all, which is exactly the failure the install-error work had just finished criticising. They belong to the package rather than to the upload: they stay true until its files change, and uninstalling clears them with the row. Both halves now answer the same question — why is a theme not behaving — so they are one panel rather than a fourth feedback channel on a screen that already had a toast, a pinned toggletip and a confirmation dialog. Nothing in it is dismissible, because every row is derived from state the loaders or the option already hold: a row disappears when the thing it describes is fixed, and a dismissal could only hide a true statement. It is empty on a healthy site. The grid's empty state also stops claiming no themes are installed when there are theme folders present that all failed to load.
- `themes/README.md` §4 describes registration as it now behaves. It still said the first registered theme is the fallback "whenever a folio's stored `theme_id` is empty or unrecognised", which stopped being true when those two cases were separated — an unrecognised ID now 404s rather than rendering as whichever theme sorted first, and an empty one prefers the theme set in Settings. It also said a declared dependency is simply required, without noting that a missing one now skips the theme. And it said nothing about the thing most worth knowing before editing a theme on a live site: the loaders run at plugin-include time, before `plugins_loaded`, so a syntax error in any theme file is a site-wide fatal that takes wp-admin with it, and `__()` does not work in the loaders at all.
- The "Package format" panel points at the spec instead of retelling it, and gets smaller doing so. Three paragraphs of contract sat under the zip tree, paraphrasing `themes/README.md` — which is how this panel came to describe a package that would not work, asking for `assets/thumbnail.png` when images resolve from `assets/images/`. What is left is the two facts the tree cannot show and a packager cannot infer — that the name becomes the ID, so a second upload is refused rather than treated as an update, and that image filenames are whatever `setup.php` declares — plus one line saying the full spec ships with the plugin at `themes/README.md`. It always has: there is no packaging step, so the file is already sitting in `wp-content/plugins/` on every install, and nothing anywhere said so.
- `themes/README.md` caught up with the code in five places it had drifted. It said a theme need not fill "all eighteen" `--folio-*` slots when the contract has carried twenty-two core slots since `--folio-focus`, `--folio-on-ground` and the two accent-2 tones were added. `default_title` and `image_set` appeared nowhere in 951 lines despite `folio-starter/setup.php` declaring both — the sets and the roles each answers to are now a table, read out of `pexels/sets.php`, which matters because `sample_image_slug()` returns an empty string for a role it does not recognise and says nothing. `sample-content.php` was missing from the folder anatomy although every built-in theme ships one. §10's install-validation list stopped at six checks when there are now eight, and did not mention that the two added are what turned a white screen on `admin-post.php` into an error message. And §12 advised preferring intrinsic sizing over a breakpoint without noting that the checker reports a layout with exactly one — an author following the prose precisely got warned by the tool, which is the worst way to learn a rule exists.
- The Themes screen is laid out with the same grid the rest of the plugin uses. It was the one admin page building its own: a hand-written `.g-themes-page` capped at 1200px, `.g-themes-section` re-declaring the white card that Overview and Settings already spell out in utilities, and two bespoke CSS grids — an `auto-fill` track of 210px minimums for the theme cards and a `1.6fr / 1fr` split with its own 960px media query for the upload row. None of that was wrong on its own; it just meant the screen answered to a different set of breakpoints than every page beside it, so a window width that put Settings into one column left Themes in two. The page is now a `space-y-4` stack of `bg-white border border-gray-200 rounded-lg shadow-sm p-4` sections with the same `text-sm` heading and `text-gray-600` description as everywhere else, the theme cards run on `grid-cols-1 sm:grid-cols-2 lg:grid-cols-3 xl:grid-cols-4`, and the upload row takes the `xl:grid-cols-3` thirds grid the Collection Tags tab already had, with the spans reversed so the dropzone keeps the wider column it had under the old `1.6fr / 1fr` — the same shape as before, expressed in the breakpoints the plugin shares. The section headers lost their underline, which nothing else on any other screen draws. Fifty-two lines of now-unreferenced CSS came out of `groove-main.css`; the theme card, dropzone and details dialog keep their own styles, which are component work rather than layout.
- Every built-in theme's description says what the theme does instead of who it is for. "For consultancies and digital agencies", "designed for weekly digital publications" and "for long-form eBooks" each told a reader who else the theme was meant for, which is no help in choosing one and wrong the first time somebody uses it for something it never named. What replaced them is the thing the theme actually gives you: Proposal's fourteen blocks and its accent taken from the cover image, Magazine's colorway built per page and contrast-checked, eBook's seven book blocks and its chapter bar. Newsletter's description also stopped claiming "accessible preset color systems", which have not existed since the preset meta was retired — its palette is generated from the reader's own time of day, and now says so.
- The theme details dialog shows a theme with both of its pictures at once: the cover photograph fills the frame, and the thumbnail the card was showing sits on it as an inset. Each answers a different question — the photograph is what a new folio starts with, the same image the folio editor’s "Use default" restores; the thumbnail is the layout underneath it, and it is what ties the dialog to the card that opened it, which a cover cropped to a 21:9 band on its own never did. The pair sits beside the facts rather than above them, so the dialog is one screenful on a laptop instead of scrolling its own actions out of sight. A wash at the foot of the photograph keeps the inset legible over whatever the picture happens to be doing there, and a theme whose setup.php declares no cover shows its thumbnail full-frame with no inset rather than a broken image. The Built-in / Installed and Default badges moved up beside the name in the header, where what a theme is called and what kind of theme it is read as one line. "Updated" is shown in the site’s own date format rather than the bare ISO string the theme wrote, and opening the dialog no longer parks a focus ring on the close button.
- Every `Page` theme class inherits its folio lookup, pagination and heading-anchor helpers from `Base_Theme` instead of carrying its own copy. `get_folio_data()`, `get_current_index()`, `get_prev_page()`, `get_next_page()`, `to_anchor_name()` and `get_html_id()` were the same code in four themes — three of them byte-identical, Groove Magazine differing only in indentation — and quietly divergent in the fifth, which is the failure mode copy-paste always has: Groove Proposal had hardened four of the six, and the fixes could not travel, because there was nowhere for them to travel to. The base now carries the hardened versions, so a sixth theme inherits them rather than copying whichever file it was told to start from. What stays theme code is what genuinely differs — which headings a theme collects, how it turns blocks into HTML, and every `display_*()` method.
- The shared drawer controller moves focus into a pane with `focus({ preventScroll: true })`, and ignores a `transitionend` that bubbled up from something *inside* the pane — a link tinting under the cursor — rather than treating it as the pane having finished animating. Every pane that opts in today is fixed-position, so neither could misbehave yet; both are wrong the moment a theme opts a pane in that sits in normal flow, which is exactly what Groove Proposal's contents dropdown nearly became.
- The two shared nav handlers in `assets/js/groove-main.js` are opted out of by attribute rather than by a hardcoded list of theme class prefixes. Both used to filter on `.closest('.gn-page, .gp-page')` — shared infrastructure naming two themes' private CSS prefixes, so a new theme could neither join nor leave the behaviour without editing shared code, and neither could tell from its own files that the behaviour existed. A theme whose own JS paints the top bar now says `data-groove-navbar="own"` on the bar; one that opens its own sections panel says `data-groove-nav-toggle="own"` on the toggle. Saying nothing gets the shared handler, which is the right answer for almost every theme. This is the same shape as the `data-groove-drawer` opt-in already used for drawer behaviour, in the other direction.
- The seeded sample eBook sets its figures as plates rather than `core/image` — a bleeding frontispiece in the foreword and two numbered figures running in one sequence across the chapters, the way a book numbers them. Its closing rule is the theme's own section break rather than a `core/separator`, so the book uses one kind of divider throughout instead of two that look nothing alike. The plates' attribute JSON carries markup, since the credit holds the Pexels links, so the seed escapes `<`, `>`, `&` and `--` exactly as `@wordpress/blocks` does — a seeded block is now byte-identical to the one the editor writes back the first time the page is saved.
- Groove eBook's chapter bar is frosted rather than opaque. Past the first screenful it used to go fully solid, because at any lower opacity the running text passing under it read straight through; a blurred backdrop lets it stay a translucent plane instead and dissolve what passes beneath, and it gains a hairline in that state — frosted white over the white reading card has no edge of its own. Its unscrolled colour is unchanged; only the blur is added there. The mobile contents dropdown is deliberately left opaque: it carries accent-coloured links, which the same frosted surface would drop to 4.39:1 over the folio's blue ground, under the 4.5:1 floor. Engines without `backdrop-filter` keep the opaque bar.
- Web fonts load in one consistent way, and only where a theme is actually rendered: a folio cover or page (published or previewed), the theme-picker preview, the password gate, and the block editor for a folio page. Three mechanisms were replaced — the render-blocking `@import` at the top of Groove Magazine's and Groove Newsletter's `theme.css`, and the hardcoded Google Fonts URL that Groove Proposal enqueued from `cover.php`, `page.php` and `blocks.php`. The block editor's copy loaded Fraunces and Inter on *every* folio page, whichever theme the folio used; it is now gated on the edited folio really being a Groove Proposal, and follows that folio's own font choices.
- Folio Starter and Groove eBook now actually load the typefaces they name (Inter, DM Sans). Both listed them as the family to use but never fetched them, so with no folio font selected they rendered in whatever the reader's system supplied.
- Font stylesheets are enqueued without a `?ver=` query string and paired with a `preconnect` to `fonts.gstatic.com`, which nothing hinted at before, so the font files start downloading a round trip earlier.
- The password gate resolves its typography through the same resolver as the themes, so it is typeset like the folio behind it — including the theme's defaults, which it previously ignored — in one request rather than two `<link>` tags.
- Theme covers moved from PNG to the curated JPEGs, retiring 24MB of source art that included three byte-identical copies of the same 7.7MB placeholder.
- Seeded folios are always created as drafts, whatever the site's default folio status. Sample copy and stand-in photography used to go live the moment a folio was created; the draft status flows through to the seeded pages, and the analytics event reports what was actually created rather than what was intended.
- The default folio title setting can be left blank, which means "let the theme decide"; the Settings field previews what the currently selected theme would produce. An explicit setting still wins everywhere.
- A folio that cannot be shown says which of the three things went wrong — the folio is missing, it is not viewable yet (a draft opened without a session allowed to see it), or its theme is genuinely unregistered — instead of always reporting "Theme not found." and sending people hunting for a broken theme. All three still return 404, so an unpublished folio does not confirm its own existence.
- The collection filter pills follow the admin colour scheme accent like the rest of the plugin chrome, instead of a fixed legacy blue.
- A folio base slug that cannot be used in a URL is now reported instead of silently replaced with "folio". Substituting a slug behind the operator's back moved every published folio to a URL they had not asked for, and then showed the substitution back to them as if it were their own choice.
- All Folios column widths are fixed rather than content-driven, so filtering by collection no longer shifts every column sideways. They are set as percentages proportional to each column's floor width and always summing to 100%, so the table stays fluid and every column shares in the space a wide window offers, rather than one column absorbing all of it — Collection Tags used to grow to 669px of em-dashes at a 1624px container while Folio Name stayed pinned at its 340px minimum and Last Updated wrapped. Each breakpoint re-splits the percentages across the columns still standing. (The widths have to be plain percentages: under `table-layout: fixed` a width mixing `%` and `px` is discarded outright and the column falls back to `auto`.)

### Removed
- `is_first_page()` and `is_last_page()`, which four themes each declared and nothing anywhere called.
- The in-plugin Feedback page and everything behind it: the `groove-feedback` admin screen and menu item, the `groove_feedback` post type, the hourly WP-Cron retry, and the `feedback_submitted` PostHog event. Collecting feedback meant holding a real email address and free text on a US host, which is a data-protection commitment worth making deliberately rather than by default. Passive analytics stays — it is anonymous, opt-in, and creates no person profile.
- Submissions already stored on a site are left in place, unregistered and invisible, rather than deleted. The retry schedule is unhooked once on upgrade so it stops firing with nothing to answer it.
- With the Feedback page gone there is no in-plugin contact route at all; the Support page it replaced is not coming back with it.
- Usage analytics, entirely. `includes/analytics.php`, the PostHog project key, the `groove_usage_analytics` opt-in and all six `track()` call sites are gone. The plugin now makes no request to StudioEN or PostHog under any circumstance, so there is no consent to collect, no key to rotate and no processor to name in a policy. At this scale the events answered *what happened* and never *why*, which is the only question worth asking of a few dozen installs.
- Settings → Privacy is now a statement rather than a form. It says plainly that nothing is collected, and lists the two requests the plugin genuinely makes — Google Fonts, fetched by the reader's own browser when a folio renders, and Pexels, only with the operator's own key and only when they ask for it. A panel claiming "we collect nothing" while a folio silently hands every reader's IP to Google would have been true about us and misleading about them.
- On upgrade the plugin clears the feedback retry cron and deletes the `groove_usage_analytics` option once, so no site is left recording consent to something that no longer happens.
- The "Read our Privacy Policy" link at the foot of Settings → Privacy. It arrived with the analytics that are now gone, to name the processor behind them, and it pointed at `groove.studio/privacy`, which 404s — on a domain the plugin's own headers do not use. A dead link is bad anywhere and worse on the one panel whose whole job is to be believed: an operator who follows it to check the claim above it finds a missing page. It was not repointed at the policy that does exist, on studioen.us, because that policy is about the studioen.us website — comments, cookies, Gravatar, embedded content — and says nothing about this plugin. Sending someone there looks like an answer and is not, which is a worse failure than the 404, because it does not announce itself. What stays is the panel, which discloses more than a general policy could: it names Google Fonts and Pexels, says which of the two the reader's browser contacts without being asked, and stays true because it lives beside the code it describes. A policy link earns its place again when the plugin sends something this panel cannot account for.

### Fixed
- Groove Newsletter's focus ring lied to anything reading the contract. `applyPalette()` set `--gn-focus` at runtime, and `theme.css` declares `--gn-focus` as `var(--folio-focus)` — so the ring rendered in the live time-of-day palette while `--folio-focus` stayed on its stylesheet literal, which is exactly the failure README §7 spends forty lines warning about. The JS had it grouped under a comment reading "privates with no slot: theme.css holds a literal for each of these", which was true of its neighbours and not of this one. It sets the slot now, and the alias picks the value up on the way through.
- The compiled Tailwind is committed, as the docs have always said it should be. `.gitignore` carried a bare `build` rule — sitting with `dist`, `exports` and a leftover `.strapi-updater.json`, so generic boilerplate rather than anything meant for this plugin — and `assets/build` is the only build directory in the repo, so the rule caught it. There is no packaging step here: the plugin ships as this repo, and `modules/groove-main/module.php` reads `assets/build/.vite/manifest.json` at runtime to find the stylesheet. A clone-and-deploy without someone remembering to run `npm run build` therefore loaded every admin screen with no styles at all, which is a failure the repo has been one step away from the whole time and nothing would have reported.
- Two themes claiming one ID no longer swap places in silence. `register()` writes to the registry keyed on the derived ID, so the later one simply overwrote the earlier: the displaced theme left the picker with nothing said, and every folio storing that ID rendered as something else. The later one still wins — a package the operator installed deliberately supersedes what was there, which is the answer an upload already gets — but the displacement is now recorded against the theme that lost, since that is the one somebody is looking for and cannot find, and it appears in the Themes screen's problem panel with the way to undo it. Install refuses this collision outright, so reaching it means the two arrived separately: a plugin update shipping a built-in whose name derives to an ID some installed package already answers to.
- `Themes_Manager::register()` refuses a theme whose derived ID is empty, and the loaders stop emitting a PHP warning for a `setup.php` they cannot read. The ID is `sanitize_title(get_name())` and no loader guard checks `name` — they check `cover_class` and `page_class`, not the one key the ID comes from — so a manifest declaring both classes and no name took the registry key `''`. That is worse than not registering: `has('')` then answers true while `resolve_registered_theme_id()` treats `''` as "never assigned" and returns the default, so the two disagree about the same theme, and `get_all_themes()` puts a nameless entry in every picker and settings dropdown. Separately, the built-in loader tested `setup.php` with `file_exists()` while testing the two view files with `is_readable()`; a manifest that was present but unreadable passed that guard, and the `include` a line later emitted a warning on every request before the `is_array()` check caught it anyway. Both files are now tested the same way.
- An installed theme package whose classes no longer extend `Base_Theme` took the whole site down on every request. `load_installed_themes()` guarded `register()` with `class_exists` alone, where `load_builtin_themes()` has always checked `is_subclass_of` as well — and `register()` opens with `$cover_class::get_id()`, a method such a class does not have. The resulting `Error` is thrown while the plugin file is still being included, before `plugins_loaded`, with nothing above it to catch anything, so the front end, wp-admin, REST and cron went together and the operator could not reach the Themes screen to remove the package that did it. Recovery meant FTP. Install validates this now, but that only ever covered packages installed since; a package already on disk, or edited in place afterwards, arrived here unchecked. The two loaders now run the same two guards in the same order.
- A theme that declares a dependency it does not ship registered anyway, and fataled on the first visitor. The loaders skipped an unreadable `dependencies` entry in silence and carried on — and because dependencies declare functions rather than classes, nothing downstream noticed: `cover.php` still parsed, `class_exists()` was still true, the theme still appeared in the picker with a thumbnail and a description. The failure surfaced as `Call to undefined function` on the front end, on a theme every admin screen reported as healthy. A theme that cannot render is now left out of the picker instead, which is the same answer the loaders already give to every other kind of broken theme. `bin/check-theme-contract.php` described this case backwards — "the require fails and the folder is skipped silently", when the require was never attempted and the folder was not skipped — and now says what actually happens.
- Every reason a theme package can be rejected now says what to do about it, in a message that stays on screen and can be translated. The thirteen `WP_Error`s in `Themes_Manager` were bare English literals — the only user-facing strings in the plugin with no `__()` around them — and five of them named a fault without naming a fix: `class_conflict` did not say which class clashed, `bad_dependency_path` did not say which path, and `class_not_found` stood for four different causes at once. Two failures were worse than that: pressing Install with no file, or a remove with no theme named, redirected with the literal slugs `upload_failed` and `missing_theme_id`, which is what the operator then read in the toast. Each rejection now carries the fault as its message and the fix as its error data, and each interpolates the thing it is complaining about. Delivery changed to match. `Toast::error()` put the explanation on screen for six seconds and then stripped it from the URL, so it could not be re-read by reloading; these go through `Toast::failure()` instead, which is what `includes/toast.php` built the pinned toggletip for — the hint stays on the Install button until it is dismissed. The pair travels in a per-user transient rather than the query string, because both halves are sentences now and a URL is no place for them. An uninstall failure passes no anchor: the Remove button lives in the details dialog, which the redirect has closed, so there is nothing left on screen to point at and the toast reports alone.
- A folio whose theme failed to load rendered as a different theme instead of saying so. `create_cover_theme()` and `create_page_theme()` fell back to the first entry in the registry whenever the stored `theme_id` was unrecognised, exactly as readily as when it was empty — so a theme that lost one of `load_builtin_themes()`' seven silent guards, or a folio left behind by a renamed theme, came back as Folio Starter at HTTP 200: a finished-looking page, nothing in the log, and no way for the author to find out the theme they wrote never registered. The two cases are now told apart. An empty ID still defaults — that is a folio created by wp-cli or an import, which is legitimate — and it now prefers the configured default theme before falling back to whatever sorted first, which is what that setting was for. An ID that is set but unregistered returns null. That is also what makes the "Theme not found" notice reachable: it has been in `folio-preview-template.php` all along, correctly worded, and could not run on any site with at least one working theme, which is every site, because five ship built in.
- A theme package whose classes load but do not extend `Base_Theme` fataled the install instead of failing it. `load_builtin_themes()` has checked `is_subclass_of` since it was written; the install path checked only `class_exists`, then called `register()`, which opens with `$cover_class::get_id()` — a method such a class does not have. The upload died on `admin-post.php` with WordPress' generic critical-error page: no toast, no error text, nothing naming the package. It now returns a `bad_base_class` error naming which of `cover_class`/`page_class` is wrong and what it points at.
- The theme cards on Add New no longer show a white crescent in each corner. The card draws an 8px corner with a 2px border, which curves its padding box at 6px, and both the thumbnail and the name strip under it kept the card's own 8px — so each child bulged past the border it sits inside and a sliver of card background showed through at every corner. On an unselected card that sliver is white against a grey hairline and nobody sees it; on the selected one the border is the accent colour, and the sliver reads as a gap between the picture and the selection. The inner radius is derived from the card's radius and border width now, both declared in one place, so the two cannot drift apart again if either moves. The picker inside a folio never had this — its cards clip their children — and the Add New card cannot do the same, because the Selected badge hangs off its top-right corner and would be cut in half. The same pass retires the doubled hairline between thumbnail and name, where the thumbnail and the strip were each drawing one, and two Tailwind classes that have not existed since the v4 upgrade and so were styling nothing (`aspect-w-16`, `aspect-h-9`).
- A theme card on Add New keeps its hover border once the selection leaves it. The hover colour was written in the markup and never in the class swap, so the card the screen opens on — the one that starts selected — had none to begin with and stayed inert under the cursor for the rest of the session, while every other card reacted.
- The "Package format" panel on the Themes screen described a package that would not work. It asked for `assets/thumbnail.png`, `assets/cover.png` and `assets/logo.png`; every image is resolved from `assets/images/`, under whatever filename `setup.php` declares, so an author following the diagram exactly got a theme that installed cleanly and then showed three broken images in the picker with nothing to explain why. The panel also omitted `assets/css/theme.css`, which `Base_Theme` enqueues unconditionally whether or not it exists — the one file whose absence produces an entirely unstyled theme and a 404 rather than an error. It marked only `setup.php` as required when `cover.php` and `page.php` are equally hard requirements, rejected with `missing_files` before anything is copied, and said nothing about `cover_class` and `page_class`, whose absence is the other install-time rejection. The tree itself was indented by the six tabs of PHP source it sat inside, because the surrounding markup's whitespace is part of a `<pre>`, so it rendered shifted a third of the way across its own panel. What replaces it is the structure the five shipped themes actually share, with the requirements stated in prose beneath rather than as annotations inside the diagram, and a note that a name already registered must be uninstalled before a package of the same name can be re-uploaded — the theme name being the ID means a second upload is refused rather than treated as an update.
- Groove Proposal's seeded sample logos resolve from the theme's own folder rather than `GROOVE_URL`. It was the only theme building an asset URL by hand, and the hardcoded `themes/groove-proposal/…` path is only correct while the theme ships inside the plugin — the same theme installed as a package under `wp-content/groove-themes/` would have served four broken logos on the one page meant to demonstrate the logo strip. `themes/README.md` also had the cover filename as `theme-cover.png` in its anatomy tree, its `setup.php` example and its new-theme checklist; every theme ships and declares `theme-cover.jpg`, so a theme author following the spec named a file that was not there.
- `bin/check-theme-contract.php --help` printed its own leading `*` characters down the left margin. The regex meant to strip them had `\*ic?` where it wanted `\* ?`.
- A theme folder with no `setup.php` was skipped by the checker without comment, which is precisely the failure it exists to name — it is how `load_builtin_themes()` drops a theme in silence. Any folder carrying one of a theme's four files is now treated as a theme package making a claim, and told what it is missing.
- Groove Proposal's "On this page" panel could never open. The panel is `display: none` until it gains `.visible`, the theme's own script only ever *removes* that class, and the one handler that would have added it was suppressed by the hardcoded `.gp-page` filter in `groove-main.js` — a filter written on the assumption that a theme appearing in it owned the behaviour. The theme styled the button, its hover state and the panel throughout, so the intent was never in doubt; only the opener was missing. The button now takes the shared handler, and the pane carries `data-groove-drawer` so it also answers Escape and a click outside, which a bare toggle cannot give it.
- The same panel is now a dropdown hanging from the sticky mobile header rather than a block in the page flow. It used to render as the first child of `<main>`, so the first time it could actually open it opened at the top of the document — two screens above a reader who had scrolled, who saw nothing happen at all. Taking it out of flow is also what stops opening and closing it shifting the content underneath, which had been landing every in-page smooth scroll short by the panel's own height. It gains the elevation shadow Groove Proposal had already authored and nothing had ever painted, and a backstop height cap for short viewports; the contents list inside it was already capped and scrollable, and now stops its scroll chaining to the page behind, which the panel's opt-out from the drawer scroll lock had left free. It is also painted only where the sticky header it now lives in is, so it no longer appears at desktop widths.
- Groove Proposal's "Back to top" button ran two scrolls per press — `groove-main.js` scrolls that button to the top for every theme, and the theme had also bound its own smooth scroll to the same click, so an instant jump was followed by a smooth no-op. The duplicate is gone. Its "On this page" toggle also declares `aria-expanded` at render rather than gaining it on first click, so it is announced as a disclosure before anyone touches it.
- Four themes could render a page with an empty nav, no prev/next links and no folio title. `get_folio_data()` resolved the parent folio through `WP_Query` alone, which misses it under some post-status filtering; Groove Proposal had added a direct `get_post()` fallback with an explicit viewability check, and the other four never received it. The fallback now lives on `Base_Theme`, so every theme has it.
- The admin icon font's `@font-face` pointed its `woff` and `truetype` sources at `assets/fonts/`, a directory that does not exist. Browsers fell through to the `woff2` beside it, so nothing looked broken, but two of the five sources were dead URLs.
- Folio bulk actions run on `admin_init`, before WordPress emits the admin header. They were called from `display_content()`, by which point the header was already sent: PHP warned, the redirect silently did nothing, and the action stayed in the URL so a refresh re-submitted it.
- Saving one settings tab no longer undoes another. Every tab fell through to one of two branches in the save handler, so saving General reset the routing base slug to "folio", and saving Routing turned the usage analytics opt-in off — while never saving the slug the operator had just typed, which is what they had pressed the button for. Each tab now writes only its own options.
- Deleting a collection tag that was already gone reported success. `wp_delete_term()` returns `false` rather than a `WP_Error` for a term that does not exist, and only the error case was checked.
- Groove's accent tokens resolve on `<body>`, where WordPress publishes the admin colour scheme (`body.admin-color-*`), instead of `:root`, where several block-package stylesheets still leave a legacy `#007cba` behind. A `var()` is substituted where the property is declared, so the plugin's highlights — filter pills, theme cards — froze that stale blue and rendered a different colour from core's own primary buttons on the same screen.
- The All Folios screen sat inside two nested `<div class="wrap">` — one from the shared page base, one of its own — so core's `.wrap` margin applied twice and the screen carried 40px of inset on its right against 4px on its left. The page header and the table also disagreed about where the left edge was, by the 2px the inner wrapper added. There is one wrapper now, and the table sits on the same insets as every other admin list table. The `overflow-x: auto` that rule carried is gone with it: it made `.wrap` a block formatting context, and a BFC refuses to overlap a float, so the screen would have shrunk away from the Screen Options tab by its full width down the whole height of the page. Nothing needs to scroll, because the column drops keep the table inside the width it has.
- Below 782px, where WordPress stacks each list-table row into a card, the "Folio Name" label rendered on top of each folio title instead of beside it. Core labels every stacked cell from its `data-colname` and the rule catches the primary cell too — the one cell that needs no label, because the title is the row.
