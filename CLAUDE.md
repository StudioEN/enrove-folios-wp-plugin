# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Enrove Folios — a WordPress plugin (PHP 7.1+, WP 5.9+) for authoring multi-page documents ("folios") that render through self-contained themes, bypassing the site's WordPress theme entirely. Bootstrap is [enrove-folios.php](enrove-folios.php); everything else hangs off [includes/plugin.php](includes/plugin.php).

## Commands

```bash
npm install
npm run dev            # Vite dev server on :5173 (the plugin auto-detects it — see "Admin assets")
npm run build          # → assets/build/ + .vite/manifest.json (commit the build; PHP reads the manifest)

php bin/check-theme-contract.php            # conformance check for every theme's CSS + PHP contract
php bin/check-theme-contract.php --theme=enrove-ebook --strict    # --strict exits non-zero on warnings (CI)
php bin/check-theme-contract-selftest.php   # the checker's own test suite (37 cases × 2 subject themes)
php bin/check-docs.php                      # the two theme docs render cleanly and their anchors resolve
php bin/check-docs.php --verbose            # ...and show the offending line for each problem

php bin/curate-pexels.php --help            # build-time image curation; needs a Pexels key (see README)
```

There is no PHP unit-test suite. `check-theme-contract-selftest.php` is the only automated test; run it after touching `check-theme-contract.php`.

**[themes/README.md](themes/README.md) and [themes/BUILDING-A-THEME.md](themes/BUILDING-A-THEME.md) are rendered in wp-admin** (Enrove → Themes → *Spec* / *Playbook*), by `Enrove\Utils\Markdown` ([utils/markdown.php](utils/markdown.php)) — a renderer for the Markdown those two files use, not Markdown in general. Syntax it does not implement renders as literal asterisks and pipes rather than raising anything, so **run `php bin/check-docs.php` after editing either file**. It rejects images, footnotes, reference links, strikethrough, raw HTML, autolinks, HTML entities, `_underscore emphasis_` and setext headings, and it verifies that every anchor linked to — inside a document, and from [pages/themes.php](pages/themes.php) via `Enrove\Utils\Theme_Docs` — still names a heading that exists. [folio-embed-regression-checklist.md](folio-embed-regression-checklist.md) is a **manual** checklist to run whenever folio page or theme rendering changes.

## Architecture

### Bootstrap and the autoloader

`Plugin::instance()` (singleton, [includes/plugin.php](includes/plugin.php)) registers the autoloader, boots `Themes_Manager::register_defaults()`, wires filters in its constructor, then runs `init()` on `init` priority 0.

[includes/autoloader.php](includes/autoloader.php) resolves `Enrove\Foo\Bar_Baz` → `foo/bar-baz.php` relative to the plugin root: strip the `Enrove\` prefix, split camelCase on hyphens, `_` → `-`, `\` → `/`, lowercase. **A new class file's path must match its namespace** or it silently never loads. A short explicit map at the top of the file covers the exceptions.

### The four managers

| Manager | Registers |
|---|---|
| `Contents_Manager` ([contents/](contents/)) | CPTs `enrove_folio` + `enrove_folio_page`, the `enrove_collection_tag` taxonomy, and all `register_post_meta()` calls |
| `Menu_Manager` ([menu/](menu/)) | Admin menu items on `admin_menu` prio 20; each `Menu_Item` wraps a `Page` and delegates `render()` to `$page->display_page()` |
| `Modules_Manager` ([modules/](modules/)) | Admin-side feature modules; today just `enrove-main`, which enqueues everything |
| `Themes_Manager` ([themes/](themes/)) | Folio themes (built-in only; the .zip installer was removed in 0.5.1 — WordPress.org forbids writing PHP to `wp-content/`) |

Admin screens are `Enrove\Pages\*` classes extending [pages/page.php](pages/page.php) (`Page extends Assets`), each with a `PAGE_ID` const (`enrove-overview`, `enrove-all-folios`, `enrove-folio`, `enrove-add-new`, `enrove-themes`, `enrove-settings`). A `Page` registers its menu item from its own constructor via the `enrove/menu/register` action, and POST handlers via `add_post_action()` (→ `admin_post_*`). List views use [list/](list/) `WP_List_Table` subclasses.

### Front-end routing — no rewrite rules, by design

`Plugin::add_rewrite()` is deliberately empty. Adding rewrite rules makes WP see a CPT archive query, and since `has_archive => false`, `redirect_canonical` bounces the visitor home before templates run. Instead a `template_redirect` hook at **priority 5** (ahead of `redirect_canonical`) intercepts and `exit`s:

- `?enrove_theme_preview=` → [includes/theme-picker-preview-template.php](includes/theme-picker-preview-template.php), after `Plugin::read_theme_preview_request()` has checked `edit_posts`, the picker's nonce and the theme. The template reads no request data itself; it is handed `$theme_id`, `$view` and `$page_index`
- a path under `/{base_slug}/`, or `?enrove_preview=1`, or `?folio_id=` / `?p=` naming an enrove post → [includes/folio-preview-template.php](includes/folio-preview-template.php), unless `?enrove_print=1` and `Folio_Print::get_requested_folio()` accepts the folio → [includes/folio-print-template.php](includes/folio-print-template.php), handed `$print_folio`. A folio the request may not see carries on to the gate or the notice as usual

That template resolves the theme, renders the password gate or a 404, and otherwise emits a bare document around `$theme->display_theme()`. Don't hardcode `/folio/` — the base slug is the `enrove_folio_base_slug` option; call `Utils::get_folio_base_slug()`, and build every folio URL with `Utils::get_folio_permalink_by_id()`.

### Themes

**Read [themes/README.md](themes/README.md) before touching anything under `themes/`** — it is the authoritative spec (folder anatomy, `setup.php` manifest, `Base_Theme` lifecycle, font contract, markup conventions, migrations). There is also a `enrove-folios-theme` skill covering this work. Highlights that bite:

- A theme's ID is `sanitize_title()` of its `name` in `setup.php`, never declared. The folder name must match it; renaming `name` orphans every folio storing the old ID.
- The plugin was Groove Folios until it was renamed Enrove Folios, and every name went with it: the namespace, post types, taxonomy, options, meta keys, CSS classes, file names, the uploads folder, theme IDs and block names. [setup/legacy-names.php](setup/legacy-names.php) (`Setup\Legacy_Names::migrate()`, first thing in `Plugin::__construct()`) moves a site's existing data from the old names to the new, once. It is the only file that spells the old names, each one in full; a new stored name needs no entry there.
- `Themes_Manager::load_builtin_themes()` skips a malformed theme folder rather than failing. It is no longer silent: each skip is recorded by `record_skipped_theme()` as a reason code, and the problem panel on Enrove → Themes names the folder and the fault. A theme missing from the picker failed one of its guards — read the panel before reading the code.
- **Theme loading happens at plugin-include time**, before `plugins_loaded` and on every request, so a broken theme file can white-screen the whole site, wp-admin included. Only *one* of the four ways that happens is actually uncatchable (class redeclaration); the other three are site-wide fatals merely because the loaders do not `try` around the `require`. themes/README.md §13 has the table and the fix. Two follow-ons: `__()` does not work in the loaders (text domain not loaded yet), and anything a loader wants to report must be stored as data and turned into a sentence later.
- A `display_theme()` override must start with `if (!parent::display_theme()) { return; }` — that call is what loads the data.
- Themes never load fonts themselves. Declare a `fonts` block in `setup.php`; [themes/font-loader.php](themes/font-loader.php) loads them, and **only from uploads**: `Font_Library` ([themes/font-library.php](themes/font-library.php)) downloads every family into `uploads/enrove-folios/fonts/` when an admin presses Download Fonts on Settings → Fonts. Never load a font from Google's CDN on a render path — WordPress.org rejected that as phoning home. Font variables are injected on a selector that requires the cover root to carry `g-folio__theme-cover` and the page root's class attribute to **end** in `-page`.
- [assets/css/folio-contract.css](assets/css/folio-contract.css) defines the `--folio-*` token slots. A theme points its private tokens *at* the slots (`--my-surface: var(--folio-surface)`), never the reverse, and redeclares the slots — not the aliases — in its scheme blocks.
- A theme declares its password-gate colours as a `gate` block in `setup.php` (`accent`, `accent_hover`, `background`, all hex). There are no colour maps in `folio-preview-template.php` any more — they were plugin source no packaged theme could join, so the rule was unsatisfiable for third parties.

**Saving as a PDF** is the browser's own printing: there is no PDF library and no server step, and JavaScript cannot get at the file, so it always goes through the print window. `Enrove\Themes\Folio_Print` ([themes/folio-print.php](themes/folio-print.php)) puts the cover, a contents page and every page in one document, each page through the theme's `display_article()` with `$is_print_mode` set, inside `get_print_root_class()`. Build the URL with `Utils::get_folio_print_url()`. [assets/css/folio-print.css](assets/css/folio-print.css) is the shared layer and each theme's `assets/css/print.css` finishes it. What cost real time to learn, all of it verified against PDFs, not assumed:

- `target-counter()` and `string()` are in no browser, and nothing says where the browser will break a page. Prediction drifted, so [assets/js/enrove-print.js](assets/js/enrove-print.js) sets the breaks: a hidden frame lays the flow out in columns one sheet tall, a block ending within 10mm of the foot moves on, and each block that starts a sheet gets `break-before: page` in the real document. **Every block in the flow has `break-inside: avoid`**, or a sheet can end at a break the script cannot set. Tables are the exception: their rows are the blocks, a table up to half a sheet moves whole, and a longer one splits between rows and repeats its head. A wide table's `overflow-x: auto` has to go, as a scroll box cannot break across sheets.
- The flow prints smaller than the screen: `zoom: var(--g-folio-print-scale)` on the contents and each page, 0.75 (16px to 9pt), and 0.8 in Enrove Proposal, whose text starts at 15px with a lot of 12px beside it. `zoom` and not a font size, because themes size type in px, rem and tokens alike. On the flow's children and not the flow, so the flow stays one sheet wide for the script. A section therefore lays out wider than the sheet in CSS pixels, so a length meant for the paper is divided by the scale (`calc(120mm / var(--g-folio-print-scale))`), and running text needs holding to `--g-folio-print-measure` in `print.css`, or 9pt runs past a hundred characters a line.
- `vw` in print is the content width of the **first** sheet. The zero-margin cover makes it the paper's width, so anything in the flow sized in `vw` is larger on paper than measured. **Pin every `vw` that reaches a page in `print.css`.** A cover with margins does not work: Chrome clips to the page area, so a transform or negative margin cannot reach the edge, and overflow to the right shrinks the whole document to fit.
- **The document names no paper.** Given a `size`, the print window fits the sheet to its own paper, which leaves white strips on the cover (A4 on Letter down the sides, Letter on A4 at the top and foot, with the browser's date and URL back inside them), and a printer's Paper size setting is an ordinary way to get there. So `@page` has no `size`, and the cover is `100vh` and fills what the window gives it. The script lays out on `Folio_Print::SHEET_WIDTH` by `SHEET_HEIGHT`, A4's width and Letter's height, which fits both: the flow stays that wide on Letter, and `margin-bottom: calc(100% - 257.4mm)` holds the text to that height on any paper, because a block too long for a sheet splits wherever the sheet ends, and a taller sheet moved everything after it. If the top or bottom margin changes, change that calc and the constants together. `collectBlocks()` steps into `block` and `flow-root` boxes only: a wrapper of any other display hides its blocks from the script, the breaks fall where the paper puts them, and it shows only when the papers disagree. To print on a given paper, use `Page.printToPDF` with `preferCSSPageSize: false`.
- Firefox needs its own rules, under `@supports (-moz-appearance: none)`, tested on 159 through a real `window.print()` (silent, to Save to PDF, from a profile's prefs) and through the real print window over Marionette (`.claude/spikes/pdf-export/ffdlg.py`, with `MOZ_REMOTE_ALLOW_SYSTEM_ACCESS=1`), because the Margins dropdown's `honorPageRuleMargins` has no pref and a silent run cannot reach it. It has no forced column break: `CSS.supports('break-before', 'column')` is false, so in the measuring frame `pushToNextColumn()` fills the rest of a column with a spacer, only for what is still on the current sheet, and the spacers do not count in the indices sent to the real document. Its `vh` and `vw` in print are the paper less half an inch a side with Margins on Default and the whole paper with None, whatever `@page` says, and the media width tells the two apart, which sets `--g-folio-print-sheet-height`. Its cover is `position: absolute; height: 100%` of a root at 100%, leaving a slot that starts the sheet: `height: 100%` on the body as well stops the flow paginating. It draws its own header in a top margin and its own footer in a bottom margin, the address and date among them, and draws neither where a sheet has none, so from 126 `@page` has no margins there and the flow's padding with `box-decoration-break: clone`, which repeats it on every sheet, does their work. It has no margin boxes, and `counter(page)` prints 0, so the frame picks a block on each sheet (`findFeet()`) and the real document adds a `.g-folio-print__foot` to it, moved to the foot of the sheet with a relative offset. What did not work: a fixed element is the same on every sheet and clipped to the page area in Firefox and WebKit, and an absolute one lands on the first sheet unless a positioned box on its own sheet holds it, and moves to the next sheet once it passes the foot of the text area. A foot past the foot of the sheet does the same, wrongly numbered. In its PDFs a link goes to the last sheet its target reaches, so a contents link is aimed at the section's first block and not the section, which can span sheets. Its title stays on one line and ends in an ellipsis, as a fourth line lands on the next sheet. A foot goes in the last place in a block, as a first child would take the first letter of a drop cap; a block that runs on to another sheet takes it to the wrong one, so a sheet filled by one paragraph has no footer. Look every host up before adding any foot, as a foot moves every position after it. The flow clips, as Firefox shrinks the whole document to fit an overflow. With all that the five sample folios match Chrome sheet for sheet, on both papers and both Margins settings. Before 110 it has no named pages, and before 126 no `zoom`, and those versions keep the old margins and the bar says to update.
- Only Chrome, Edge and Firefox reach the edge of the sheet. WebKit takes one set of margins from the first sheet for the whole document and ignores a named `@page`, so `@page :first { margin: 0 }` takes the margins off every sheet. Safari keeps a white margin round the cover, and `@supports (font: -apple-system-body)` in `folio-print.css` shortens the cover to fit a sheet, which there holds less than its size says, and drops the contents page's numbers: its layout on paper differs from the one the script measures, and it has no margin boxes. Media queries see a desktop there, so `zoom: 0.5` lays the cover out at a desktop's width and scales it down, or it clips and collides on the narrow sheet. It also prints a gradient or a mask that fades to nothing as solid black, so a theme's `print.css` swaps those for flat tints under the same query (Magazine, Newsletter): the test is WebKit's print path, which is `wk_print.swift`, not Safari itself. A browser cannot write `TrimBox`, `BleedBox` or crop marks, and `@page`'s `bleed` and `marks` are in no browser, so a press-ready file needs a PDF tool after the browser. Test the real print window with `--kiosk-printing` and a profile whose sticky print settings pick Save as PDF: it matched `--print-to-pdf` sheet for sheet.
- A media query in print ignores `@page`: about 741px on any paper in headless Chrome, and set by the print window in a real one. Paper is about 660px, so themes get their phone layouts, and core stacks Columns below 782px. `print.css` restores what breaks.
- A script cannot turn off Headers and footers, but `@page` can. Chrome and Edge draw their own text only where a document leaves a margin to itself: the bottom boxes alone removed the URL and left the date and title, so `@top-center { content: "" }` is there for its presence, and with both claimed the option leaves Chrome's print window. A first sheet with no margin hides the option too, but the kiosk test still printed headers on the later sheets, so a covered folio relies on the box as well. Test this with no sticky setting, as a first-time reader has it on.
- `position: fixed` repeats on every sheet (hence `.g-folio-print__cover > *`), a closed `<details>` does not print, a lazy image is blank unless it has loaded, `document.fonts.ready` resolves at once until layout has asked for a font, and a hidden frame may never get an animation frame.
- Test with fonts downloaded (Settings → Fonts) and on both papers. The bugs above did not show on system fonts or on one paper size, and a folio with a paragraph taller than a sheet shows what a tidy sample does not. So does realistic content: tables, buttons and a short opening paragraph under a drop cap found bugs the sample content never touched.

`bin/check-theme-contract.php` mechanically checks most of the above. It reads CSS as text and tokenises PHP rather than executing it, so it runs on a bare checkout with no WordPress. No `bin/` script ships in the release zip: nothing at runtime loads the checker since the theme installer went.

### Folio ↔ page linkage

A `enrove_folio_page` belongs to a folio via `folio_id` post meta. It is written once, when post-new.php creates the page's auto-draft from an Add Page link: `Contents\FolioPage\Content::verify_add_page_link()` (on `load-post-new.php`) checks that link's nonce, whose action names the folio (so `folio_id` is the one value read before it), then `edit_post` on the folio. Build the link with `Content::get_add_page_url()`. No save hook reads a folio from the request or the Referer, and admin code (the block editor, `Theme_Blocks::get_editor_folio_id()`) reads the meta. On the front end **resolution is URL-first, meta second**: use `Base_Theme::resolve_page_folio_id()` in `Page` subclasses rather than reading the meta directly. `includes/plugin.php` keeps the slug in sync with the title. Page order within a folio is `menu_order`.

The other way pages are created is **import** ([contents/folio-page/import.php](contents/folio-page/import.php), `Contents\FolioPage\Import`): copies of existing posts and pages, from the folio editor's Import posts and pages dialog, opened from Add Page's split-button menu (`Folio::render_import_dialog()`, handler `Folio::import_pages()`) or Import posts and pages in the Add New dialog, where the same picker is the dialog's second screen rather than a dialog over it (`Folio::render_import_screen()`; Done takes the selection back to the themes, and Continue there makes the folio with `Add_New::create_folio()`). Both read the picks with `Import::read_form($nonce_action, $nonce_field)`, which verifies the form's own nonce itself so the nonce sniff passes with `--ignore-annotations`, and make the pages with `Import::create_pages()`, which writes `folio_id` and `_enrove_source_post_id` (the source; a copy is never linked back). Only sources the user may `edit_post` are importable. Classic content arrives as `converted[<id>]` blocks from the browser and is held to `Base_Theme::get_content_allowed_html()`; without them the source is copied with `wpautop()`. The server does not strip script text from posted blocks (a wrapper around `wp_unslash()` fails the sanitising sniff): the converter strips `<script>`/`<style>` whole, and so does the fallback. The conversion itself is `wp.blocks.rawHandler()` after `wp.autop.autop()`, run in a hidden iframe ([contents/folio-page/block-converter.php](contents/folio-page/block-converter.php), `Block_Converter`, admin-post `enrove_block_converter`) because it needs `wp-block-library`, several MB: never enqueue that on an Enrove screen. The parent page talks to it through `window.enroveBlockConverter` (`preload()`, `convert()`), same-origin `postMessage` both ways. `[gallery]` converts to image blocks with only an attachment ID, so `Import::get_source()` sends the URLs, only of attachments the user may `read_post` (the IDs come from the post's text), and the converter fills them in.

**A page goes live with its folio, never ahead of it.** [contents/folio-page/publishing.php](contents/folio-page/publishing.php) (`Contents\FolioPage\Publishing`) enforces it where posts are written, so every save path obeys: `wp_insert_post_data` saves a publish/future/private page as a draft while its folio is not `publish` or `private`, `rest_pre_insert_enrove_folio_page` refuses the same with a 409, `rest_prepare_enrove_folio_page` drops the `wp:action-publish` link so the block editor offers only Draft and Pending, and the `folio_id` meta hooks take down a live page moved into an unpublished folio. `follow_folio_status()` (`transition_post_status`) is the one cascade, whatever changed the folio (its editor, Quick Edit, cron, trash): leaving a live status takes the live pages down, noting each one's status in `_enrove_status_before_folio`; going `publish` puts those back as they were and publishes the other draft and pending pages the user may publish, while going `private` brings back only the pages that were private (a `publish` page is readable at its own URL whatever its folio's status). `save_folio()` has no page loop of its own. `follow_page_status()` puts back a page `wp_publish_post()` published ahead of its folio (it writes past `wp_insert_post_data`), and `before_delete_post` takes down a force-deleted folio's pages. **Inside the class, change a page's status only through `set_page_status()`**, which puts the stored title, content and excerpt back as the last `wp_insert_post_data` step: a bare `wp_update_post()` re-runs them through the current user's save filters (kses, and from WP 7.0 the block custom CSS stripper), which strip an administrator's embeds and block CSS for anyone without `unfiltered_html`, cron included. Do the same anywhere else a plugin path changes only a status. A WordPress import (`WP_IMPORTING`) is left alone, and duplicating a folio does not copy the held-status meta. The folio editor's Publish and Unpublish confirm first (`Folio::display_publish_dialog()`, counted with `Publishing::get_pages_to_publish()`). On the front end a page is viewable only where its folio is (`Utils::can_current_request_view_post()` checks the folio first: private, password-locked and unpublished folios keep their pages too). That covers the plugin's own routes; WordPress's own addresses for a page (the REST API and its search endpoint, `?enrove_folio_page=<slug>`, feeds, searches, the sitemap) are closed by [contents/folio-page/visibility.php](contents/folio-page/visibility.php) (`Contents\FolioPage\Visibility`), which leaves out pages whose folio the request may not see and sends a folio or page found at a core address to its folio URL. A new way of listing or serving pages needs the same treatment, and a folio lists its pages with `Utils::get_listed_page_statuses()`: published only in a live folio, for editors too, plus private to whoever may read them (so an editor's PDF of a live folio has its private pages), and every viewable status in an unpublished one (a preview); use it, not `get_viewable_post_statuses()`, for any page list. `Publishing::migrate_existing_pages()` (on `admin_init`, so on the first wp-admin, admin-ajax or admin-post request) took down, once, the live pages older versions left in unpublished folios (`enrove_page_publishing_migration_v1`).

### Request parameters

WordPress.org review asks for a nonce check before any `$_GET`/`$_POST`/`$_REQUEST` read, read-only view parameters included; phpcs:ignore justifications were not accepted. So on admin screens:

- **View parameters** (which folio, tab, list filter/search/sort/page, and action outcomes such as `bulk_action`) are read only through `Enrove\Utils\Request` ([utils/request.php](utils/request.php)), which verifies a `_enrove_view` nonce before reading. Build every admin link that carries one with `Request::admin_url()` (or `Folio::get_edit_url()`), add `Request::nonce_field()` to a GET form, and sign redirects the same way. An unsigned link reads as the default view.
- **Which screen this is**: core's `global $plugin_page` / `$pagenow`, not `$_GET['page']`.
- **Handlers** verify their nonce first, before reading any field (bulk forms: check `isset()` of the nonce field, `check_admin_referer()`, then read `action`), then check a capability on the object the input names. A form or link that acts on one object names it in the nonce action (`Folio::get_save_nonce_action()`, `Import::get_form_nonce_action()`, `'enrove_delete_collection_tag_' . $term_id`); its ID, read with `absint()`, is then the one value read before the check.
- **Front-end routing** (`folio_id`, `p`, `enrove_preview`, `enrove_print`, and the theme picker preview's `enrove_theme_preview`, `enrove_preview_view`, `enrove_preview_page`) uses registered query vars and `get_query_var()` (`Utils::ROUTE_QUERY_VARS`); public URLs cannot carry nonces. The picker preview's own nonce (`_wpnonce`) is the one superglobal read on that path, inside a method, before anything else. **No request data is read at a file's top level**: a template included from a handler is handed checked values.

`php <plugin-check>/vendor/bin/phpcs --standard=WordPress --sniffs=WordPress.Security.NonceVerification --ignore-annotations` over the shipped files should report nothing.

### Admin assets

[modules/enrove-main/module.php](modules/enrove-main/module.php) (`is_active()` → `is_admin()`) is the single enqueue point. Tailwind 4 comes from the Vite dev server when a GET on `/@vite/client` returns 200 from localhost:5173 (probed only on a `local`/`development` site, for a request from localhost; Vite answers HEAD there with a 404), otherwise from `assets/build/.vite/manifest.json`. The dev-server code lives in [modules/enrove-main/vite-dev.php](modules/enrove-main/vite-dev.php) (`Vite_Dev`), which the package script leaves out of the zip, so a released plugin has no localhost code; `module.php` uses it only if the class loads. Keep anything that talks to localhost in that file. Hand-authored CSS/JS under `assets/css` and `assets/js` is enqueued directly and versioned by `filemtime()`. Load order matters: `enrove-toggletip` → `enrove-toast` → `enrove-main`. PHP config reaches JS through `window.ENROVE_SETTINGS`.

**Header buttons at phone width.** The page header (`Page::display_nav()`) wraps below 782px instead of holding its 56px row. From 600px down, a header item with `'overflow' => true` leaves the bar for the More actions menu (`Page::display_overflow_menu()`, a `.g-menu` driven by `initMenu()` in enrove-main.js); `'menu_text'` gives it a fuller label there. A link item is repeated as a link; an action item needs an `id`, and its menu entry presses that real control, so the control's own script and state still apply. Feedback that control shows on itself (a tooltip) must fall back to a toast when it is hidden, as Copy link does. Keep the actions that commit work (Save, Publish) out of the menu. An item with a `'menu'` array is a split button (`Page::print_split_button()`): its own action plus a chevron menu run by the same `initMenu()`; with `'overflow'` its menu entries go into More actions after it, each a link or an action with an `id`.

All admin pages get `body.enrove` via an `admin_body_class` filter — the CSS scope for the whole plugin.

**A Tailwind utility loses to core admin CSS.** Tailwind 4 compiles utilities into `@layer utilities`, and an unlayered rule beats a layered one whatever its specificity — `:where()`-wrapped utilities like `space-y-*` have no specificity to begin with. So on any admin screen, `wp-admin/css/common.css` wins: `p { font-size: 13px; line-height: 1.5; margin: 1em 0 }`, `li, dd { margin-bottom: 6px }`, the heading rules. `text-sm`, `m-0` and `space-y-4` on a `<p>` do nothing. Utilities are safe on `div`s and `section`s, which core does not style; anything a layout depends on that lands on a text element belongs in `assets/css/enrove-main.css` as component CSS. Two notes from fixing this in the replace-theme dialog: a `margin: 0` reset there outranks the block's own `> * + *` rule, so separate children with a flex `gap` instead; and a component class used in a new place inherits none of its old container's padding — `.g-theme-details__actions` is a row *inside* the 20px-padded body, so lifting it out into a footer left the buttons on the dialog's corner and drew an edge-to-edge rule no other line in that frame has. The `.g-theme-details` dialogs keep their actions in the body for that reason; `.g-theme-picker-modal` and the first-run setup dialog (`.g-theme-details__footer`) have true, docked footers. Every Enrove dialog frame is capped at `calc(100vh - 96px)`, 48px clear above and below.

Use `\Enrove\Toast` ([includes/toast.php](includes/toast.php)) for action outcomes (`Toast::success/error/failure`); `Toast::failure()` also pins a toggletip hint to the button that was pressed. Reserve inline notices for standing conditions, not click outcomes.

**Every notification that is not pinned to a control goes through the one toast stack**, bottom-right (`.g-toast-container`): `\Enrove\Toast` from PHP, `window.enroveShowToast()` from JS, and `window.enroveStatusToast()` ([assets/js/enrove-toast.js](assets/js/enrove-toast.js)) for an operation that reports as it runs. That one is a single pill rewritten in place ("Saving…" → "Saved"); the folio editor's save status uses it. Never add a fixed-position element of your own for a message. The folio save status used to be exactly that, a separate bottom-centre pill, and the toast stack was parked in the corner to dodge it, so notifications turned up in two places. If the stack lacks something a message needs, extend `enrove-toast.js`. Feedback that belongs to one control stays at that control: toggletips for failures, the Copy link button's "Link copied" tooltip, a dialog's own status line while it is open, and Quick Edit's in-row error (as core does it).

## Conventions

- Tabs for indentation in PHP in most files (the repo is mixed; match the file you're in). `.editorconfig` covers JSON/YAML/Markdown only.
- Every PHP file starts with an `if (!defined('ABSPATH')) exit;` guard. The one exception is theme `setup.php`: the contract requires a literal array with no calls, and a direct request to one prints nothing.
- Code must pass WordPress.org's Plugin Check. That means no `<?=` short echo tags (write `<?php echo …; ?>`), no heredoc/nowdoc, output escaped late in the right context, `/* translators: */` comments on placeholder strings, and `wp_unslash()` plus sanitising on every `$_GET`/`$_POST` read. Folio page body content is escaped too, with `wp_kses($this->get_content(), static::get_content_allowed_html())` in every `page.php` (the post allowlist plus embed iframes, SVG, `<source>`, the Search form); review rejected a `phpcs:ignore` on it. A value written into inline CSS is validated where it is interpolated and the CSS passed through `wp_strip_all_tags()` at the `wp_add_inline_style()` call. A `phpcs:ignore` must name the exact sniff and give a true reason, and is no defence for escaping or nonces: review reads past them (see Request parameters). The local `.claude/scripts/pcp-lint.sh FILE…` runs the same sniffs in seconds (when present; it is not tracked).
- Text domain is `enrove-folios` (it must equal the WordPress.org slug) for all i18n, including strings copied from core. Translations load just in time; there is no `load_plugin_textdomain()` call.
- Managers and singletons follow the same `instance()` / `__clone()` / `__wakeup()` shape — copy an existing one when adding a module or content type.
- `CHANGELOG.md` is kept in prose-heavy Keep-a-Changelog form under `## [Unreleased]`; add entries there for user-visible changes.
